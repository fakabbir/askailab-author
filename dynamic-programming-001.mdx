This is the first page of a DP series, so it covers the part I wish had been written down before I started "doing dynamic programming": how to tell whether a problem qualifies, how to get the recurrence out of the problem statement, and how the size of the state space decides the implementation. Every example here is code I ran, and every number is output.

## The two properties

A problem is DP-able when it has both of these, and only both.

**Optimal substructure.** An optimal solution to the big problem contains optimal solutions to the subproblems it is built from. This is what lets me combine subresults at all. It is also what *fails* quietly: the longest *simple* path (no repeated vertices) between two nodes is not DP-able, because the optimal prefix might block the suffix that needs those vertices. The classic shortest path does have it, which is why [Dijkstra](/index) works and why "longest path" is NP-hard on a general graph. When I am unsure, I test the property directly: assume I have an optimal whole, cut out a piece, and ask whether replacing that piece with a better sub-solution would improve the whole. If it would not, my "optimal" was not optimal, so the property holds.

**Overlapping subproblems.** The same subproblem shows up from many different routes, so solving it once and reusing the answer pays. Plain recursion pays the exponential price for ignoring it.

The distinction I keep sharpest is against divide and conquer. Merge sort has optimal substructure and a recurrence, and it is *not* DP: its subproblems are disjoint, so there is nothing to reuse. The signature of DP is subproblems that overlap *heavily* — enough that the number of distinct states is far smaller than the number of paths through the recursion tree. Fibonacci is the toy version; knapsack is the real one, where exponentially many item subsets map onto only `n * W` distinct states.

## Finding the recurrence from the statement

This is the step people skip and then blame themselves for. My procedure, in order:

1. **Name the answer as a decision about the last thing.** For 0/1 knapsack: consider items one at a time; for item `i` I either take it or leave it. That binary choice at the end is the recurrence — `dp[i][c]` is the best value using items `0..i-1` with capacity `c`, and it is the max of "leave it: `dp[i-1][c]`" and "take it: `dp[i-1][c-w] + v`".
2. **Ask what the recursion needs to know to produce a unique answer.** Those quantities are my state parameters, and I want the *minimal* set. "Best value with capacity `c`" is well-defined; "best value with capacity `c` having used more than two items" is not, and a state that is not well-defined cannot be memoized. Every extra parameter multiplies the table, so I strip the ones the answer does not actually depend on.
3. **Check the choices are exhaustive and disjoint.** Take-or-leave covers every subset exactly once. If my cases overlap, I am double-counting (fatal for counting problems); if they miss a case, the answer is silently too small.
4. **Write the base case before the transition.** Empty item set, zero capacity, empty string. Half my DP bugs historically have been an off-by-one in a boundary, never in the recurrence.
5. **Count the states, then decide everything else.** That number is the subject of the next section.

## State-space arithmetic: memoization or tabulation

The cost is `states * work-per-state`, and the memory is `states * bytes-per-value`. I do this multiplication before choosing an implementation, because the two styles are not stylistic preferences — they are answers to different questions.

```python
for n, w in [(1000, 1000), (1000, 100_000), (200_000, 200)]:
    cells = n * w
    print(f"knapsack n={n} W={w}: {cells:,} cells, {cells * 8 / 1e6:,.1f} MB as int64, {cells * 2 / 1e6:,.1f} MB as uint16-indices")
```

```text
knapsack n=1000 W=1000: 1,000,000 cells, 8.0 MB as int64, 2.0 MB as uint16-indices
knapsack n=1000 W=100000: 100,000,000 cells, 800.0 MB as int64, 200.0 MB as uint16-indices
knapsack n=200000 W=200: 40,000,000 cells, 320.0 MB as int64, 80.0 MB as uint16-indices
```

One million cells: either style is fine, and I use `lru_cache` because it is shorter. A hundred million: tabulation, because a Python dict with 100M entries costs roughly ten times the 800 MB of a flat array and I would be swapping. And `n = 200000, W = 200` is the case that makes the point about *reachability*: 40M cells is fine as a table, but it is also a hint that the state parameters are badly chosen — `W` that small usually means the answer wants a different state (value-indexed instead of capacity-indexed), which is how pseudo-polynomial algorithms get replaced by genuinely polynomial ones.

The real distinction between the two styles:

| | Memoization (top-down) | Tabulation (bottom-up) |
| --- | --- | --- |
| States visited | only those reachable from the answer | all of them, unless I add pruning |
| Order required | none, recursion resolves it | I must supply a valid order |
| Stack | one frame per state depth | none |
| Cost per state | dict key hashing plus a call frame | an array index |
| Sparse state space | wins outright | wastes 100 percent of the table |
| Dense state space | loses to the array by several times | wins |
| Cycle safety | infinite recursion if the graph of states has a cycle | I notice immediately |

Memoization is the right default when the reachable set is a small fraction of the theoretical grid — string edit distance on two sequences that barely differ, or interval DP where most intervals are never asked for. Tabulation is right when the state space is a rectangular grid I will fill completely, which is most knapsack/LIS/edit-distance work. The ordering requirement in tabulation is not a detail: it is a topological order over the state-dependency graph, which is the same question as [Graph Based Algorithms](/quickstart), and a cycle in that graph means the DP is not well-defined.

For the dense case the constant factor is not small. `lru_cache` costs a tuple allocation plus a hash plus a dict lookup per call, typically 5-10x an array read in CPython.

## Worked example: 0/1 knapsack, with the items recovered

```python
def knapsack(items, capacity):
    """items: list of (weight, value). Returns best value and the chosen indices."""
    n = len(items)
    dp = [[0] * (capacity + 1) for _ in range(n + 1)]
    for i in range(1, n + 1):
        w, v = items[i - 1]
        for c in range(capacity + 1):
            dp[i][c] = dp[i - 1][c]
            if w <= c and dp[i - 1][c - w] + v > dp[i][c]:
                dp[i][c] = dp[i - 1][c - w] + v
    chosen = []
    i, c = n, capacity
    while i > 0:
        w, v = items[i - 1]
        if dp[i][c] != dp[i - 1][c]:
            chosen.append(i - 1)
            c -= w
        i -= 1
    chosen.reverse()
    return dp[n][capacity], chosen
```

```text
knapsack cap 5 -> value 7 items [0, 2] weights [2, 3] values [3, 4]
1D space-optimized value (no reconstruction): 7
knapsack: mismatches vs brute force over 150 random instances = 0
```

Items `[(2,3), (1,2), (3,4), (2,2)]` and capacity 5: the answer is 7 from items 0 and 2, total weight exactly 5. This instance is *not* a counterexample to greediness, and I checked that rather than assuming it: greedy by value-to-weight ratio takes items `[1, 0, 3]` and also reaches 7. The fractional relaxation does bound it at 7.67, which is the sanity check I run on any knapsack answer (a DP result above the fractional bound means my table is wrong). The counterexample I keep for "why DP and not greedy" is the classic one: items `[(10,60), (20,100), (30,120)]` at capacity 50, where greedy by ratio takes items 0 and 1 for 160, cannot fit item 2, and misses the optimal 220 from items 1 and 2. Fractional bound for that instance is 240, so the greedy answer is 33 percent below even the relaxation.

**Reconstruction** is the part tutorials omit and the part that pays my bills. Nobody wants the optimal *value*; they want the optimal *set*. The technique is general: walk backward from the answer state and at each step ask *which transition produced this cell*. Here the test is `dp[i][c] != dp[i-1][c]` — if the value changed when item `i` became available, item `i` was used, so I record it and drop `c` by its weight. Cost: `O(states)` extra time, no extra memory. For LIS the same walk follows a `prev[]` array instead, which is cheaper still because I stored it during the forward pass.

The alternative is to keep decisions inline (`take[i][c]` as a boolean table), which costs a second `n * W` array but lets me reconstruct without touching the values, and survives space optimization if I store it as a bitset.

## Space optimization, and what it costs me

The transition for `dp[i][*]` reads only row `i-1`, so I need two rows, or one if I iterate the capacity *backwards*:

```python
def knapsack_1d(items, capacity):
    dp = [0] * (capacity + 1)
    for w, v in items:
        for c in range(capacity, w - 1, -1):
            dp[c] = max(dp[c], dp[c - w] + v)
    return dp[capacity]
```

`O(W)` memory instead of `O(nW)`. The reverse iteration is not stylistic: `dp[c - w]` must still be *last row's* value when I read it, and descending guarantees that. Iterating ascending turns this into the unbounded-knapsack recurrence, which returns a larger answer and never errors — one of the nastier bugs in this area because the code looks identical to the correct version apart from two words.

The price is reconstruction. With one row I have thrown away every row but the last, so the backward walk has nothing to walk. My options, in order of how often I use them: keep the full table (usually affordable — 8 MB is nothing); keep a decision bitset, one bit per cell, which is 1/64th of the value table and buys back exact reconstruction; or split the problem in half, Hirschberg's trick, turning `O(nW)` memory into `O(W)` for about 2x the time. The last one matters in bioinformatics, where edit-distance tables over genome-length sequences do not fit in RAM — the same arithmetic I run on [Data size estimation](/data-size-estimation) before committing to a table.

## Worked example: longest increasing subsequence

LIS is the second shape of DP: the state is indexed by *position*, not by a budget, and the transition scans backward.

```python
def lis(seq):
    n = len(seq)
    if n == 0:
        return [], 0
    dp = [1] * n
    prev = [-1] * n
    for i in range(1, n):
        for j in range(i):
            if seq[j] < seq[i] and dp[j] + 1 > dp[i]:
                dp[i] = dp[j] + 1
                prev[i] = j
    best = max(range(n), key=lambda i: dp[i])
    out = []
    while best != -1:
        out.append(seq[best])
        best = prev[best]
    return out[::-1], max(dp)
```

```text
LIS of [3, 1, 4, 1, 5, 9, 2, 6, 5] -> [3, 4, 5, 9] length 4
brute force agrees: True
LIS: length mismatches over 120 random sequences = 0
```

Two details that are easy to get wrong. The state is "length of the best increasing subsequence *ending at* `i`", not "best within the first `i`" — that choice is what makes the transition legal, because extending a subsequence needs to know its last element. And because of it, the answer is `max(dp)`, not `dp[-1]`; taking the final cell is the most common wrong answer in this problem. `prev[i]` is recorded during the forward pass, so reconstruction is a `while best != -1` walk, reversed at the end. Strictly increasing means `<`; the moment I need non-decreasing I flip to `<=` and every test that used distinct values stops telling me anything.

The state-space arithmetic again, and this time it forces the algorithm change:

```text
LIS n=200000: O(n^2) cells = 40000000000 vs O(n log n) work = 3520000
```

Forty billion cells is not a slow program, it is a program that does not exist. At `n = 200000` the recurrence has to change, not the implementation: keep the smallest possible tail for each length and binary search it (patience sorting), which is `O(n log n)` time and `O(n)` space and recovers the subsequence through the same predecessor trick. That is the practical lesson of this page — when the cell count is unreasonable, the state definition is wrong, and no amount of array flattening fixes a bad `O(n^2)`.

## Counting, where the difference between styles bites

Counting problems expose the double-counting failure mode, and they are where I insist on "exhaustive and disjoint". Ways to make change for 11 with coins `{1, 2, 5}`:

```text
coin ways (1,2,5) for 11: tabulation = 11 brute = 11
memoized version = 11 distinct states visited = 36
  total=20: memo=29 tabulation=29 brute=29 states=65
  total=40: memo=97 tabulation=97 brute=97 states=129
```

The tabulation puts coins in the outer loop, which is what makes order irrelevant; putting the amount outside counts permutations instead, and both versions are "correct-looking". The memo version touches 36 distinct states to answer total 11, where the dense table is a fixed 4 rows by 12 columns, 48 cells, and the memo count grows with the total (`36` at 11, `65` at 20, `129` at 40) while the table grows linearly. At these sizes the dict overhead is invisible; at a million states it is the whole cost, and it is exactly the reachable-set-versus-grid gap I described above.

All three answers agree with the brute force, which is the only reason I trust the disjointness argument. I brute-force every DP I write, on inputs small enough that `2^n` or `n!` is affordable, and I let the random generator pick sizes rather than testing only hand-picked ones. The brute force is also the only defense against the failure mode I fear most: a DP that is *plausible*, returns a number, and is off by exactly the cases my recurrence never covered.

## The shape of the next problems

The recurrences above are one-dimensional or two-dimensional over an index. The shapes that break my recurrence-finding muscle are interval DP (state `[l, r]`, iterated by increasing width so the dependencies are already computed), tree DP with the parent as a state parameter (which is what makes rerooting possible), and bitmask DP over subsets at `O(2^n * n)` states. All of them are decided by the same multiplication I did here: count the states, count the work per state, and the algorithm tells you which it wants. When the inner `max` scan over `j < i` is what makes a recurrence quadratic, that is where the structures on this site earn their keep — a [segment tree](/segment-tree-in-python) turns `O(n^2)` into `O(n log n)` by answering the scan as a range query.
