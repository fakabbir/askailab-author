## The one invariant

Dijkstra keeps two sets of nodes: **settled** ones whose final distance is already known, and the rest. The invariant is narrow and it is the whole algorithm:

> When I pop a node `u` off the priority queue, `dist[u]` is the true shortest distance from the source. It never changes again.

That is why the loop can be greedy. I pick the *closest* unsettled node and freeze it. Every other unsettled node is at least as far away as `dist[u]`, because the queue is a min-heap keyed on distance.

The proof intuition is one paragraph. Suppose `u` froze at distance `d` but a shorter path existed. That path must leave the settled set somewhere, so it contains a first unsettled node `x`, and the part of the path from the source to `x` is itself a path with cost at most the total. So `dist[x] <= ` (cost of the better path) `< d`. But `x` was in the queue with a key smaller than `d`, and I popped `u` anyway. Contradiction.

Every step of that argument leans on one assumption: the path to `x` is a **prefix** of the better path, and adding more edges never makes it cheaper. That holds exactly when weights are non-negative. With a negative edge, a longer path can be a cheaper path, the contradiction evaporates, and the invariant is simply false.

## Where it breaks, verified

I ran a tiny graph with one negative edge through my own implementation.

```python
neg = {"S": [("A", 1), ("B", 2)], "A": [("C", 1)], "B": [("A", -5)], "C": []}
print("negative-edge graph, Dijkstra says:", dijkstra(neg, "S")[0])
print("the true distances are:               {'S': 0, 'A': -3, 'B': 2, 'C': -2}")
```

```text
negative-edge graph, Dijkstra says: {'S': 0, 'A': -3, 'B': 2, 'C': 2}
the true distances are:               {'S': 0, 'A': -3, 'B': 2, 'C': -2}
```

The failure mode I dislike is how quiet it is. `A` comes out right. `C` is wrong, because `A` was settled at cost 1 before `B` ever improved it to -3, so `A`'s outgoing edges were relaxed with a stale value. Nothing throws. On many negative graphs Dijkstra returns correct answers by luck, which is worse than returning correct answers by construction.

## The heap implementation, and the decrease-key problem

Here is the version I use.

```python
import heapq


def dijkstra(graph, start):
    dist = {v: float("inf") for v in graph}
    prev = {v: None for v in graph}
    dist[start] = 0
    settled = []
    heap = [(0, start)]
    visited = set()
    while heap:
        d, u = heapq.heappop(heap)
        if u in visited:
            continue
        visited.add(u)
        settled.append((u, d))
        for v, w in graph[u]:
            nd = d + w
            if nd < dist[v]:
                dist[v] = nd
                prev[v] = u
                heapq.heappush(heap, (nd, v))
    return dist, prev, settled
```

`heapq` gives me push and pop, and nothing else. There is no `decrease_key`, and there is no way to say "the entry for `C` is stale, fix it". I have three options and each is a real tradeoff.

1. **Rebuild the heap** after every improvement. That is `O(V)` per rebuild and I might as well not have used a heap.
2. **Index map (true decrease-key).** Keep `pos[v]`, the node's current slot in the backing array, and sift it up manually when its key drops. This is the textbook `O((V+E) log V)` version, and it is the one to write in C++ with a `std::set` or a paired comparator. In Python I would be reimplementing sift-up by hand against a private list, which is how you introduce off-by-one bugs into an algorithm that has none.
3. **Delegate the work to stale entries** — push a new pair for every improvement and skip old ones at pop time. This is what my code does, and the `if u in visited: continue` line is the entire cost-control mechanism.

## The lazy-push alternative

The variant I write when I do not care about the settled order:

```python
def dijkstra_lazy(graph, start):
    """No visited set: push every improvement, discard stale pops by comparing distances."""
    dist = {v: float("inf") for v in graph}
    dist[start] = 0
    pushes = 1
    heap = [(0, start)]
    while heap:
        d, u = heapq.heappop(heap)
        if d > dist[u]:
            continue
        for v, w in graph[u]:
            if d + w < dist[v]:
                dist[v] = d + w
                pushes += 1
                heapq.heappush(heap, (dist[v], v))
    return dist, pushes
```

`d > dist[u]` is the lazy-deletion guard: if the popped key is worse than what I currently believe, this entry is a fossil. The two forms agree everywhere — I checked on 500 random graphs, zero disagreements — but they differ in what they bound. The number of pushes is bounded by the number of successful relaxations, which is at most one per edge, so the heap holds at most `O(E)` entries. Measured on a 400-node random graph:

```text
graph with V=400 E=8023: lazy version pushed 1063 heap entries (2.7 per node)
```

Two pushes per node on that density, so the memory cost is invisible. On a graph where many paths improve the same node repeatedly, the heap can grow well past `V`, which is the honest argument for the index-map version: `O(V)` heap versus `O(E)` heap.

## Complexity, derived

With `V` pops and at most `E` pushes, each heap operation costs `O(log (heap size))`:

- Pops: `V` of them, `log V` each → `O(V log V)`.
- Pushes: at most `E` of them, `log E` each → `O(E log E)`.
- Relaxations: `E` edge inspections, `O(1)` each → `O(E)`.

For a simple graph `E <= V^2`, so `log E <= 2 log V`, which turns `O(E log E)` into `O(E log V)`. Adding the pieces gives `O((V + E) log V)`, and because a connected graph has `E >= V - 1`, the `E log V` term swallows `V log V`. That single line is why everyone writes the complexity as `O(E log V)`.

The counter-case matters: on a dense graph (`E ~ V^2`) the heap does ~`V^2` relaxations and pays log factors on work the scan version does for free. My no-heap version is `O(V^2)` and wins there.

```python
def dijkstra_dense(graph, start):
    """No heap: scan the frontier for the min. O(V^2), the textbook version."""
    dist = {v: float("inf") for v in graph}
    dist[start] = 0
    done = set()
    for _ in range(len(graph)):
        u = None
        best = float("inf")
        for v in graph:
            if v not in done and dist[v] < best:
                best = dist[v]
                u = v
        if u is None:
            break
        done.add(u)
        for v, w in graph[u]:
            if dist[u] + w < dist[v]:
                dist[v] = dist[u] + w
    return dist
```

## Worked trace

Six nodes, my source is `A`:

```python
GRAPH = {
    "A": [("B", 4), ("C", 1)],
    "B": [("C", 2), ("E", 5)],
    "C": [("B", 3), ("D", 6)],
    "D": [("E", 3), ("F", 2)],
    "E": [("D", 2), ("F", 6)],
    "F": [],
}
```

| Pop | Settled at | Relaxations that changed something | Queue after |
| --- | --- | --- | --- |
| `A` | 0 | `B = 4`, `C = 1` | `C(1)`, `B(4)` |
| `C` | 1 | `D = 7`; `B` stays 4 | `B(4)`, `D(7)` |
| `B` | 4 | `E = 9` | `D(7)`, `E(9)` |
| `D` | 7 | `F = 9`; `E` stays 9 | `E(9)`, `F(9)` |
| `E` | 9 | nothing | `F(9)` |
| `F` | 9 | nothing | empty |

Verified output:

```text
settle order: A(0) C(1) B(4) D(7) E(9) F(9)
distances: {'A': 0, 'B': 4, 'C': 1, 'D': 7, 'E': 9, 'F': 9}
path A->F: A -> C -> D -> F cost 9
path A->E: A -> B -> E cost 9
dist to B via A->B and via A->C->B both equal: 4 chosen parent: A
```

## Tie-breaking is a policy decision

Look at `B`: `A -> B` costs 4 and `A -> C -> B` costs 1+3 = 4. My relaxation test is strict (`nd < dist[v]`), so the first path discovered keeps the parent pointer and the second is silently rejected. That is why `prev[B]` is `A` rather than `C`, even though `C` was settled earlier and would arguably be the "better" predecessor by hop count.

Three consequences I keep in mind:

- Changing `<` to `<=` does not change distances but does change which shortest path I return, and in the lazy variant it never terminates on a zero-weight cycle: every pass re-improves the neighbor "by equality", pushing an entry each time. The settled-set version is protected by the `visited` check, which is one concrete reason I prefer it when zero-weight edges are allowed. Never use `<=`.
- If I want deterministic ordering when distances tie, I push the pair `(dist, name)` so the heap falls back to the name. That is exactly why `E` settles before `F` at cost 9 in the table above.
- If I care about fewest hops among equal-cost paths, tie-break on `(dist, hops, name)` and carry the hop count as payload. The heap's tie-breaking order is free; inventing it later is not.

`E` and `F` are also a reminder that ties are not rare — they are a property of small integer weights, and real routing graphs full of them.

## Reconstruction and its limits

`prev` is a forest rooted at the source, so a path is just a walk backwards:

```python
def path(prev, start, target):
    if prev[target] is None and target != start:
        return None if start != target else [target]
    nodes = []
    cur = target
    while cur is not None:
        nodes.append(cur)
        cur = prev[cur]
    nodes.reverse()
    return nodes if nodes and nodes[0] == start else None
```

Reconstruction gives *a* shortest path, not *the* one a human would pick, and it gives nothing about the second-best path. If I need k shortest paths, Dijkstra with a single parent map is the wrong tool — Eppstein's algorithm or a modified Yen's is the right one.

## Testing it

I do not trust a shortest-path implementation I have not cross-checked. The dense version has a completely different control flow, so agreement is meaningful:

```python
random.seed(1234)
for trial in range(2000):
    n = random.randint(2, 40)
    g = random_graph(n, 0.15, 20)
    s = random.choice(list(g))
    d1, _, _ = dijkstra(g, s)
    d2 = dijkstra_dense(g, s)
    if d1 != d2:
        raise AssertionError((trial, s, d1, d2))
print("cross-check passed: 2000 random graphs, heap version == O(V^2) version")
```

```text
cross-check passed: 2000 random graphs, heap version == O(V^2) version
lazy-push variant disagrees with the settled-set variant on 0 of 500 graphs
```

Edge cases this does not cover, so I test them separately: unreachable nodes (they keep `inf` and my `path` returns `None` rather than crashing), self-loops, parallel edges between the same pair, and a source with no outgoing edges at all.

## When I reach for something else

| Situation | Use instead | Why |
| --- | --- | --- |
| Negative weights possible | Bellman-Ford | It relaxes every edge `V-1` times, so a late improvement is not thrown away. `O(VE)`, and it detects negative cycles |
| Weights are only 0 and 1 | 0-1 BFS | A deque replaces the heap: push-front for 0, push-back for 1. `O(V+E)`, no log factor |
| Small integer weights | Dial's buckets / radix heap | Array of buckets indexed by distance, `O(E + V + W)` |
| One goal, not all nodes | A* | Same skeleton, priority `g + h`; with an admissible `h` it settles far fewer nodes |
| One distant pair on a road network | Bidirectional Dijkstra | Two searches meeting in the middle roughly halves the radius each must cover |
| Dense graph, `E ~ V^2` | `O(V^2)` array version | The log factor buys nothing when relaxations dominate |
| Any negative cycle reachable | Nothing | Shortest paths are undefined; ask for cycle detection instead |

A* deserves the emphasis for this site's readers: Dijkstra is A* with `h = 0`, so the whole implementation carries over. When I have a good heuristic, A* usually settles a fraction of the nodes, and when I do not, forcing one is how you get wrong answers with confidence.
