This page is the map for the data-structures notes on this site. Before any algorithm matters, two decisions do: how the graph lives in memory, and which ordering I traverse it in. I wrote this as the explainer I wished existed when I first had to choose between "just use a dict of lists" and something that fits in RAM at a million nodes.

## Representation, with real numbers

There are three ways to hold a graph and each one is a different set of answers to the question "what can I ask it cheaply".

| Representation | Test if edge exists | Iterate neighbours of `u` | Memory for `V` nodes, `E` edges |
| --- | --- | --- | --- |
| Adjacency matrix | `O(1)` | `O(V)`, scans a whole row | `V^2` cells |
| Adjacency list | `O(degree)` | `O(degree)` | `V + E` |
| Edge list | not supported | not supported | `E` records |

The arithmetic is what makes this decision interesting, so I ran it rather than eyeballing it. Take a realistic sparse graph, one million nodes and ten million edges:

```python
def memory_math():
    V, E = 1_000_000, 10_000_000
    csr = E * 4 + E * 4 + (V + 1) * 4
    edge_list = E * (4 + 4 + 4)
    matrix_bits = V * V / 8
    matrix_bytes = V * V
    py_dict = E * (56 + 64) + V * 64
    print(f"V={V:,} E={E:,} average degree={2 * E / V:.1f}")
    print(f"CSR adjacency list (uint32 neighbour + uint32 weight): {csr / 1e6:,.1f} MB")
    print(f"edge list (u,v,w as uint32):                          {edge_list / 1e6:,.1f} MB")
    print(f"adjacency matrix, 1 bit per cell:                     {matrix_bits / 1e9:,.2f} GB")
    print(f"adjacency matrix, 1 byte per cell:                    {matrix_bytes / 1e9:,.2f} GB")
    print(f"Python dict-of-lists-of-tuples:                       {py_dict / 1e9:,.2f} GB")
```

```text
V=1,000,000 E=10,000,000 average degree=20.0
CSR adjacency list (uint32 neighbour + uint32 weight): 84.0 MB
edge list (u,v,w as uint32):                          120.0 MB
adjacency matrix, 1 bit per cell:                     125.00 GB
adjacency matrix, 1 byte per cell:                    1,000.00 GB
Python dict-of-lists-of-tuples:                       1.26 GB
O(1) edge test needs the matrix; that costs 11,905x the CSR budget
```

Four things I take from that output.

The matrix is not "a bit slower" at this size, it is one thousand times slower in bytes and simply unavailable. Packing it to one bit per cell still costs 125 GB, so a matrix is a `V` up to maybe 20k decision, not a performance decision.

The edge list is only 1.4 times the compressed-sparse-row list, and it is the right choice when I never ask about neighbours — that is exactly the shape of Kruskal's MST algorithm, union-find and a sort, no adjacency at all.

The Python number is the one that bites: 1.26 GB for the same graph, because every `(v, w)` tuple is ~56 bytes and every inner list wastes 64 bytes of pointer overhead on top of 8 bytes per pointer. My readable `dict` of lists costs 15 times the CSR budget. When I need the list-of-lists ergonomics at scale I hold CSR arrays and index them, and the readable view becomes a debugging tool rather than the data structure.

Average degree 20 is the honest way to decide: `E / V = 10` here (20 for undirected). Anything where that ratio creeps toward the hundreds and the "sparse" assumptions in the complexity bounds start lying.

## Traversal families: what each ordering buys

BFS and DFS are the same four lines of code with one container swapped — a deque for BFS, a stack for DFS. That the two orderings produce completely different guarantees is the most useful fact in this whole area. I keep them straight by naming the guarantee, not the algorithm.

```python
from collections import deque


def bfs(graph, start):
    dist = {start: 0}
    order = []
    q = deque([start])
    while q:
        u = q.popleft()
        order.append(u)
        for v, _ in graph[u]:
            if v not in dist:
                dist[v] = dist[u] + 1
                q.append(v)
    return order, dist


def dfs_stack(graph, start):
    seen = {start}
    order = []
    stack = [start]
    while stack:
        u = stack.pop()
        order.append(u)
        for v, _ in graph[u]:
            if v not in seen:
                seen.add(v)
                stack.append(v)
    return order
```

On a small pipeline graph I used throughout this page:

```text
BFS order: ['build', 'schema', 'cache', 'ingest', 'serve', 'index']
BFS hops: {'build': 0, 'schema': 1, 'cache': 1, 'ingest': 2, 'serve': 2, 'index': 3}
DFS (explicit stack) order: ['build', 'cache', 'serve', 'index', 'ingest', 'schema']
BFS and DFS visit the same set: True
BFS == Dijkstra on unit weights: True
```

**BFS gives me layer order.** The first time a node is reached is via a minimum-hop path, which is exactly why the check above says BFS distances equal Dijkstra distances when all weights are 1. Swap the queue for a priority queue and I have Dijkstra; that relationship is the subject of [the Dijkstra page](/index). Layer order is also what I want for "everything within k steps", social-graph expansion, and the shortest path in an unweighted maze. The cost is honest: BFS holds an entire frontier, so peak memory is proportional to the widest layer, which in a broad graph is much larger than DFS's depth-bounded stack.

**DFS gives me discovery and finish times.** A recursion-tree of finish times is what makes subtrees contiguous, and that single property produces cycle detection (a back edge to something on the current stack), bipartiteness checks, and the ordering guarantees below. Its memory is a path, not a layer.

I prefer the explicit-stack DFS form in production code because it has no recursion limit, and because the stack is visible when I need to reconstruct a path. The rewrite is mechanical and it is covered on [Stack](/stack). One caveat I do not forget: the iterative version's visit order is not identical to the recursive version's unless I push children in reverse, and the order I get above (`cache` before `schema`) is a direct consequence of pushing in list order.

**DFS preorder versus postorder** is a separate axis and people conflate them constantly. Preorder is ancestor-first (serialize a tree, copy a directory). Postorder is descendant-first (delete a tree, evaluate an expression, schedule dependencies, compute subtree aggregates). My run prints both:

```text
DFS preorder: ['build', 'schema', 'ingest', 'index', 'serve', 'cache']
DFS postorder: ['cache', 'serve', 'index', 'ingest', 'schema', 'build']
```

Notice `build` finishes last in postorder and first in preorder — that is the whole distinction, and it decides whether my aggregation is correct or wrong.

## The landscape beyond traversal

**Shortest path.** Dijkstra for non-negative weights ([here](/index)), Bellman-Ford when weights can go negative, A* when I have a heuristic and one destination, Floyd-Warshall for all-pairs on small dense graphs at `O(V^3)` with ten lines of code, 0-1 BFS when weights are only zero and one. My default is Dijkstra; my mistakes have all been applying it where its non-negativity invariant did not hold.

**Minimum spanning tree.** Kruskal (edge list plus union-find, `O(E log E)`) and Prim (adjacency list plus a heap, `O(E log V)`). These are the "connect everything for least cost" family, and they are also where I meet union-find, which reappears as the backbone of offline dynamic connectivity and of clustering.

**Topological order.** Only defined for a DAG, and the only ordering that respects every edge. Kahn's indegree algorithm is what I use because it hands me the cycle case explicitly:

```python
def topo_kahn(nodes, directed):
    indeg = {v: 0 for v in nodes}
    out = {v: [] for v in nodes}
    for u, v in directed:
        out[u].append(v)
        indeg[v] += 1
    q = deque(sorted(v for v in nodes if indeg[v] == 0))
    order = []
    while q:
        u = q.popleft()
        order.append(u)
        for v in out[u]:
            indeg[v] -= 1
            if indeg[v] == 0:
                q.append(v)
    return order if len(order) == len(nodes) else None
```

```text
topological order: ['a', 'b', 'c', 'd', 'e'] -> every edge points forward: True
Kahn on a cycle returns: None
```

The `len(order) == len(nodes)` test is the important half: a partial order means a cycle, and the nodes left out are the ones trapped in it. This is build systems, DAG task schedulers, and dependency resolution. Note that topological order is not unique — I sorted the zero-indegree seeds precisely so my output is reproducible in tests, since a scheduler that reorders between runs is a debugging nightmare.

**Strongly connected components.** Tarjan's and Kosaraju's algorithms collapse a directed graph into its mutual-reachability classes in linear time. Once collapsed, the components form a DAG, and that two-step — condense, then run anything that needs a DAG — is how I reason about cyclic dependency graphs, reachability in state machines, and 2-SAT implication graphs.

**Flows.** Max-flow/min-cut, Dinic's algorithm, and bipartite matching as a flow special case. They are slower in practice than shortest path (`O(V^2 E)` for Dinic's worst case) and the modelling is where the difficulty lives: the hard part is deciding what my capacity edges are, not the algorithm.

**Graph-based clustering.** This is the family that reaches my day job. Tag and customer clustering can run as agglomerative merging (which is literally a graph: edges between clusters with a distance, merged greedily — the same shape as Kruskal), as KNN or affinity graphs where density defines neighbourhood, or as partition methods on numeric features. [Tag clustering algorithm](/tag-clustering-algorithm) records which of those I chose for the tag taxonomy and why. The graph view matters because it makes "how many clusters" a property of connectivity rather than a parameter I have to guess.

## How I choose, in practice

I ask three questions in order. What will I query — neighbour expansion, edge existence, or full edge scans? That picks the representation before anything else. How big is `V` versus `E`? That is the arithmetic above and it usually disqualifies the matrix. And is the graph directed, weighted, and acyclic? Directed and acyclic puts topological order and DP-on-DAG on the table; weighted and non-negative puts Dijkstra there; weighted with negatives removes it.

Almost every wrong answer I have produced in this area came from skipping question three and assuming non-negativity or acyclicity because the data "looked like" a tree. The structures themselves are small pieces of code; the invariants are what I have to get right.
