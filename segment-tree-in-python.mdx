These are my notes from 13 September 2026, when I finally sat down and made a segment tree something I can write from memory. What started it was a simple question: **is a segment tree available in Python by default?** The answer is no — Python's standard library includes neither a segment tree nor a tree-map, so I either write the class myself or install a third-party package from PyPI such as `segment-tree` or `pysegmenttree`.

I ended up writing it myself. What follows is the version I trust, the version I did not trust, and the arithmetic that decides between them. Every code block on this page I executed, and the printed output is the real output.

## Installing instead of writing

If I want someone else's implementation, two packages exist:

- [`segment-tree` on PyPI](https://pypi.org/project/segment-tree/) — "a general implementation that includes semigroup range operations in O(logN) time, built-in support for ma…". The generic-combine design is the interesting part; it is a segment tree parameterized by an associative operator.
- [`pysegmenttree`](https://pysegmenttree.readthedocs.io/) — "a data structure to perform efficient range queries over an array. For example, finding the sum/minimum/maximum of…".

Neither is in the standard library, and for interview or contest work I have never had them available, so the fallback is the hand-written template below. Related confusion worth clearing up: [AlgoMonster's note on TreeMap in Python](https://algo.monster/blog/python-treemap) makes the same point for ordered maps — "Python does not have builtin TreeMap. For interviews, we can normally solve TreeMap problems using hashmap + binary search". The lesson generalizes: Python ships excellent hash maps and heap queues, and stops at anything with an ordered-key or range-aggregate interface. When I need ordered keys without a package, the honest options are `bisect` over a sorted list (fine until writes dominate) or `heapq` when I only ever need the extreme. A segment tree is what I reach for when I need aggregates over *index ranges* with interleaved writes.

## The flat 2N iterative tree

The fastest, most boilerplate-free way to write a segment tree for range minimum queries is a flat 1D array of size `2N` built bottom-up. This is the template I copy:

```python
class SegmentTree:
    def __init__(self, data):
        self.n = len(data)
        # Allocate 2 * N space; 0-indexed leaves start at index N
        self.tree = [float('inf')] * (2 * self.n)

        # Insert leaves
        for i in range(self.n):
            self.tree[self.n + i] = data[i]

        # Build the tree from bottom to top
        for i in range(self.n - 1, 0, -1):
            self.tree[i] = min(self.tree[2 * i], self.tree[2 * i + 1])

    def update(self, i, value):
        """Update the element at index i to a new value."""
        pos = i + self.n
        self.tree[pos] = value

        # Move up and update parents
        while pos > 1:
            pos //= 2
            self.tree[pos] = min(self.tree[2 * pos], self.tree[2 * pos + 1])

    def query(self, left, right):
        """Get the minimum in the range [left, right] (inclusive)."""
        res = float('inf')
        left += self.n
        right += self.n + 1  # Make the boundary exclusive for the loop

        while left < right:
            if left % 2 == 1:
                res = min(res, self.tree[left])
                left += 1
            if right % 2 == 1:
                right -= 1
                res = min(res, self.tree[right])
            left //= 2
            right //= 2
        return res
```

```python
arr = [4, 1, 8, 3, 9, 2]
st = SegmentTree(arr)

print(st.query(0, 3))  # Min of [4, 1, 8, 3]

st.update(1, 10)       # Change index 1 from 1 to 10
print(st.query(0, 3))  # Min of [4, 10, 8, 3]
```

```text
1
3
```

Why this is the quickest version to write:

- **No recursion.** Iterative `while` loops, avoiding recursive overhead and any recursion-depth limit in Python.
- **Simple math.** Left child is always `2 * i`, right child is always `2 * i + 1`, parent is `i // 2`.
- **Comfortable bounds.** Queries take the inclusive `[left, right]` form even though the loop internally converts `right` to exclusive.

## The mental model: a tournament bracket

If the input has `N` elements, the tree array has size `2N`. The original data occupies the second half, starting exactly at index `N`. The first half (indices `1` to `N-1`) holds the winners of ranges.

```text
Array: [ _,  (Root),  (L-Child), (R-Child),  [Leaf 0], [Leaf 1], [Leaf 2], [Leaf 3] ]
Index:   0      1          2          3          4          5          6          7
        └────────── Parent Nodes ──────────┘ └───────────── Original Data ────────────┘
```

Three navigation rules:

1. **Move to a leaf.** Original index `i` lives at `i + N`.
2. **Find children.** Node `i` has children at `2 * i` and `2 * i + 1`.
3. **Move to parent.** Divide by two: `i // 2`.

Index 0 stays unused; it is padding so that the child arithmetic works out of `1`.

## The same thing as three functions

When I do not want a class, the three blocks are highly predictable. This one is for sums:

```python
def build(arr):
    n = len(arr)
    tree = [0] * (2 * n)

    # 1. Put leaves at the back
    for i in range(n):
        tree[n + i] = arr[i]

    # 2. Fill parents working backwards
    for i in range(n - 1, 0, -1):
        tree[i] = tree[2 * i] + tree[2 * i + 1]  # Change '+' to min/max if needed
    return tree


def update(tree, n, i, val):
    pos = i + n
    tree[pos] = val

    while pos > 1:
        pos //= 2  # Move to parent
        tree[pos] = tree[2 * pos] + tree[2 * pos + 1]  # Merge children


def query(tree, n, left, right):
    res = 0
    left += n
    right += n + 1  # Make boundary exclusive

    while left < right:
        if left % 2 == 1:  # Odd index: grab value, step right
            res += tree[left]
            left += 1
        if right % 2 == 1:  # Odd index: step left, grab value
            right -= 1
            res += tree[right]
        left //= 2
        right //= 2
    return res
```

```python
data = [5, 2, 8, 1, 4]
n = len(data)
tree = build(data)
print("sum(0,4) =", query(tree, n, 0, 4))
update(tree, n, 2, 10)
print("sum(1,3) after update(2,10) =", query(tree, n, 1, 3), "(naive:", sum([2, 10, 1]), ")")
```

```text
sum(0,4) = 20
sum(1,3) after update(2,10) = 13 (naive: 13 )
```

## Memory tricks that keep it correct

- **Size is 2N.** Never guess. `4N` is only needed for the harder recursive version — see the sizing section below.
- **Loop bounds.** The build loop runs `n - 1` down to `1`.
- **The "odd" rule.** In `query`, a node is included in the result only when its index is odd (`% 2 == 1`). That single rule is the entire boundary logic; if my query is wrong, an odd check is usually the culprit.

The odd rule deserves one more sentence because it is where people give up and go recursive. An odd index is a *right* child. If my left pointer sits on a right child, that node's range is not covered by its parent within my window, so I must take it into the answer and step past it. The same argument mirrored on `right` produces the other branch. If both pointers are even, their parent is fully inside the window and I climb a level without grabbing anything.

## Choosing the array size

Three sizes circulate and I used to use them interchangeably, which is how I once corrupted a tree. They are not interchangeable.

`2 * n` — exactly what the flat iterative layout above needs. Every node has an index below `2n`, and no slot is wasted, because the leaves are packed contiguously at `n .. 2n-1`. This holds for *any* `n`, not just powers of two, and that surprise is the main reason I prefer the iterative layout.

`2 * 2^ceil(log2 n)` — the same compactness, but with the array padded to a full binary tree. `ceil_pow2(6)` is 8, so a 6-element array needs 16 slots rather than 12. I pay up to 2x waste (when `n` is just above a power of two) and get a perfectly regular structure in exchange: every node's covered range is a power-of-two block, which is what makes recursive builds and lazy propagation easy to reason about.

`4 * n` — the defensive bound for the *pointer-free recursive* layout where node `i`'s children are `2i` and `2i+1` but the tree is built by range-splitting rather than by index arithmetic. Because splits are uneven, some node indices can drift above `2n`. It is a safe over-approximation and I only want it when I am writing the recursive-array variant by hand.

```python
def ceil_pow2(n):
    return 1 << (n - 1).bit_length()


size = ceil_pow2(6)
print("ceil_pow2(6) =", size, "-> tree array length", 2 * size)
```

```text
ceil_pow2(6) = 8 -> tree array length 16
```

And the layout itself, with `inf` padding for the two phantom leaves:

```python
class Pow2Tree:
    def __init__(self, data, combine, identity):
        self.n = len(data)
        self.size = ceil_pow2(self.n)
        self.combine = combine
        self.identity = identity
        self.tree = [identity] * (2 * self.size)
        for i in range(self.n):
            self.tree[self.size + i] = data[i]
        for i in range(self.size - 1, 0, -1):
            self.tree[i] = combine(self.tree[2 * i], self.tree[2 * i + 1])

    def point_trace(self, i, val):
        steps = []
        pos = i + self.size
        self.tree[pos] = val
        while pos > 1:
            pos //= 2
            self.tree[pos] = self.combine(self.tree[2 * pos], self.tree[2 * pos + 1])
            steps.append((pos, self.tree[pos]))
        return steps
```

```python
t6 = Pow2Tree([4, 1, 8, 3, 9, 2], min, float("inf"))
print("pow2 tree before:", t6.tree)
print("climb after update(3, 0):", t6.point_trace(3, 0))
print("pow2 tree after: ", t6.tree)
print("query min(0,5) =", t6.tree[1])
```

```text
pow2 tree before: [inf, 1, 1, 2, 1, 3, 2, inf, 4, 1, 8, 3, 9, 2, inf, inf]
climb after update(3, 0): [(5, 0), (2, 0), (1, 0)]
pow2 tree after:  [inf, 0, 0, 2, 1, 0, 2, inf, 4, 1, 8, 0, 9, 2, inf, inf]
query min(0,5) = 0
```

Note the identity value appearing in real slots. Index 7 covers leaves 6 and 7, both padding, so it is `inf` — which is exactly right, since an empty range must contribute nothing to a `min`. Choosing `identity` wrong is the classic bug in this layout: `min` wants `inf`, `max` wants `-inf`, `sum` wants `0`, and a product wants `1`. And `combine` must be associative; the tree never checks, and a non-associative operator (subtraction, or floating-point addition with wildly different magnitudes) gives answers that depend on the tree shape.

## Worked point-update trace

The single most useful thing to be able to draw on paper is the climb. For `Pow2Tree([4, 1, 8, 3, 9, 2], min, inf)` updating index 3 to `0`, with `size = 8`:

| Step | Position | Range it covers | New value | Why |
| --- | --- | --- | --- | --- |
| Leaf | `3 + 8 = 11` | `[3, 3]` | `0` | written directly |
| 1 up | `11 // 2 = 5` | `[2, 3]` | `0` | `min(tree[10], tree[11]) = min(8, 0)` |
| 2 up | `5 // 2 = 2` | `[0, 3]` | `0` | `min(tree[4], tree[5]) = min(1, 0)` |
| 3 up | `2 // 2 = 1` | `[0, 7]` | `0` | `min(tree[2], tree[3]) = min(0, 2)` |

Three parents, one per level, and the loop stops because `pos` reached 1. That is `ceil(log2 n)` writes: `O(log n)` per update, with no allocation and no recursion. Nodes 6 and 7 and their subtree are untouched, which is the whole point of the structure — an update repairs only the ranges that actually contain the index.

## Build cost: iterative versus recursive

Both builds are `O(n)` in combines, and the difference is in the constant and the memory shape.

The iterative build runs `n - 1` combines: one per internal node, in a single tight Python `for` over a flat list. No function calls, no objects, cache-friendly. For a million elements that is roughly a million `min` calls.

The recursive build does the same `n - 1` combines but pays a function call per node — about `2n` calls total — plus the frame overhead, plus one object per node if I use the pointer version. Recursion depth is only `ceil(log2 n)`, so I will not hit `setrecursionlimit` with a sane `n`; the cost is the call count and the allocation, not the depth. Concretely: `n - 1` combines in both cases, `2n - 1` nodes touched in both, and the iterative version never leaves the list.

| | Flat `2N` iterative | Recursive array (`4N`) | Pointer class |
| --- | --- | --- | --- |
| Code length | short | medium | longest (class boilerplate) |
| Memory | efficient flat array, exactly `2n` ints | flat array, up to `4n` ints | one object per node with pointer addresses |
| Mental load | index arithmetic and the `% 2 == 1` rule | range arguments `l, r, node` | standard DFS, most intuitive |
| Build work | `n - 1` combines, no calls | `n - 1` combines, `2n - 1` calls | `n - 1` combines, `2n - 1` calls, `2n - 1` objects |
| Advanced features | hard to add lazy propagation | possible, awkward | natural place for lazy propagation or dynamic allocation |

## The pointer class version

Using a `Node` class with `left` and `right` pointers is the most intuitive way to build a segment tree. It mirrors how a binary search tree or a merge sort is built, so during an interview I spend my attention on the problem instead of on index math. This uses a top-down recursive strategy, and instead of doing math on array indices each node represents an explicit range `[L, R]`: a range of one element is a leaf, otherwise the node splits in half with the left child taking `[L, mid]` and the right child `[mid + 1, R]`.

```python
class Node:
    def __init__(self, start, end):
        self.start = start
        self.end = end
        self.val = float('inf')
        self.left = None
        self.right = None


class SegmentTreePointer:
    def __init__(self, arr):
        self.root = self._build(arr, 0, len(arr) - 1)

    def _build(self, arr, l, r):
        """Recursively builds the tree and returns the root node."""
        node = Node(l, r)

        # Base case: Leaf node
        if l == r:
            node.val = arr[l]
            return node

        # Split range into two halves
        mid = (l + r) // 2
        node.left = self._build(arr, l, mid)
        node.right = self._build(arr, mid + 1, r)

        # Merge step
        node.val = min(node.left.val, node.right.val)
        return node

    def update(self, index, val, node=None):
        """Updates the value at a specific index."""
        if node is None:
            node = self.root

        # Base case: Found the exact leaf node
        if node.start == node.end:
            node.val = val
            return

        mid = (node.start + node.end) // 2
        if index <= mid:
            self.update(index, val, node.left)
        else:
            self.update(index, val, node.right)

        # Recalculate current node's value after child update
        node.val = min(node.left.val, node.right.val)

    def query(self, l, r, node=None):
        """Queries the minimum value in the range [l, r] (inclusive)."""
        if node is None:
            node = self.root

        # Case 1: Node range is completely inside query range [l, r]
        if node.start >= l and node.end <= r:
            return node.val

        # Case 2: Node range is completely outside query range [l, r]
        if node.end < l or node.start > r:
            return float('inf')

        # Case 3: Node range partially overlaps
        left_min = self.query(l, r, node.left)
        right_min = self.query(l, r, node.right)

        return min(left_min, right_min)
```

```python
arr = [4, 1, 8, 3]
st = SegmentTreePointer(arr)

print(st.query(0, 2))  # Min of [4, 1, 8]

st.update(1, 10)       # Update index 1 from 1 to 10
print(st.query(0, 2))  # Min of [4, 10, 8]
```

```text
1
4
```

The three-case query is worth memorizing even if I never write this class: full cover returns the cached value, no cover returns the identity, partial cover recurses. Those three cases are what every tree decomposition reduces to.

## Lazy propagation: range updates

Everything above handles a *point* update plus a *range* query. The moment I need to add `+v` to a whole range and still answer range queries, the iterative template stops working — a point update repairs one root-to-leaf path, while a range update would need to repair `O(k log n)` paths and the tree is no longer worth its cost. That is what lazy propagation fixes: I stop at a fully covered node, update its aggregate, and stash the pending work in a tag for my children to absorb later.

```python
class LazySegmentTree:
    def __init__(self, data):
        self.n = len(data)
        self.size = ceil_pow2(self.n)
        self.tree = [0] * (2 * self.size)
        self.lazy = [0] * (2 * self.size)
        for i in range(self.n):
            self.tree[self.size + i] = data[i]
        for i in range(self.size - 1, 0, -1):
            self.tree[i] = self.tree[2 * i] + self.tree[2 * i + 1]

    def _push(self, node, span):
        if self.lazy[node] and span > 1:
            for child in (2 * node, 2 * node + 1):
                self.lazy[child] += self.lazy[node]
                self.tree[child] += self.lazy[node] * (span // 2)
        self.lazy[node] = 0

    def add(self, l, r, value, node=1, nl=0, nr=None, span=None):
        if nr is None:
            nr = self.size - 1
            span = self.size
        if nr < l or r < nl:
            return
        if l <= nl and nr <= r:
            self.tree[node] += value * (nr - nl + 1)
            self.lazy[node] += value
            return
        self._push(node, span)
        mid = (nl + nr) // 2
        self.add(l, r, value, 2 * node, nl, mid, span // 2)
        self.add(l, r, value, 2 * node + 1, mid + 1, nr, span // 2)
        self.tree[node] = self.tree[2 * node] + self.tree[2 * node + 1]

    def sum(self, l, r, node=1, nl=0, nr=None, span=None):
        if nr is None:
            nr = self.size - 1
            span = self.size
        if nr < l or r < nl:
            return 0
        if l <= nl and nr <= r:
            return self.tree[node]
        self._push(node, span)
        mid = (nl + nr) // 2
        return self.sum(l, r, 2 * node, nl, mid, span // 2) + self.sum(
            l, r, 2 * node + 1, mid + 1, nr, span // 2
        )
```

```python
raw = [1, 2, 3, 4, 5, 6]
lz = LazySegmentTree(raw)
print("initial sum(0,5) =", lz.sum(0, 5))
lz.add(1, 3, 10)
print("after add(1,3,+10): sum(0,5) =", lz.sum(0, 5), "sum(1,3) =", lz.sum(1, 3), "sum(2,2) =", lz.sum(2, 2))
print("naive check:", sum([1, 12, 13, 14, 5, 6]), sum([12, 13, 14]), 13)
```

```text
initial sum(0,5) = 21
after add(1,3,+10): sum(0,5) = 51 sum(1,3) = 39 sum(2,2) = 13
naive check: 51 39 13
```

Three details make or break this code. `tree[node] += value * (nr - nl + 1)` scales the tag by the node's *width* — forgetting the width is the single most common lazy-propagation bug, and it makes sums drift while point queries still look right. `_push` must run before descending, and only when `span > 1`, since a leaf has no children to hand the tag to. And `self.lazy[node] = 0` has to happen on every push, otherwise the same increment lands twice.

Both operations stay `O(log n)`; lazy propagation does not reduce the work per update, it stops me from doing `O(k)` work for a `k`-element range. If the operation does not distribute over range length the way addition does — say "assign a constant" — then the tag becomes a set instead of an accumulator and I need to track whether it is pending at all.

## Cross-checking before I trust it

I do not ship a segment tree I have not randomized against. The pattern: generate a small array, interleave random updates and random queries, and compare against the naive slice.

```python
random_ok = True
import random

for trial in range(300):
    m = random.randint(1, 40)
    base = [random.randint(-50, 50) for _ in range(m)]
    flat = SegmentTree(base)
    naive = base[:]
    for _ in range(60):
        if random.random() < 0.4:
            i = random.randrange(m)
            v = random.randint(-99, 99)
            flat.update(i, v)
            naive[i] = v
        else:
            l = random.randrange(m)
            r = random.randrange(m)
            if l > r:
                l, r = r, l
            if flat.query(l, r) != min(naive[l : r + 1]):
                random_ok = False
                break
print("randomized cross-check flat RMQ vs naive min: passed =", random_ok)
```

```text
randomized cross-check flat RMQ vs naive min: passed = True
```

The lazy version gets the same treatment, and it is the one I actually need it for, because an off-by-one in `_push` produces answers that are wrong only after a specific sequence of overlapping ranges:

```text
randomized cross-check lazy tree vs naive range add/sum: passed = True
```

`n` as small as 40 is enough. The value is in covering the awkward shapes — `n` not a power of two, queries of width 1, and updates whose range boundary straddles a node — and the padding-to-power-of-two path in particular is where a hand-written 2N tree quietly differs from a padded one.

## Adapting it, and when not to

Changing the operator is a two-line edit: `min` becomes `max` (identity `-inf`) or `+` becomes `*` (identity `1`, and watch out for zeros), in all three places — build, the update climb, and the query accumulator. That is the entire generalization, and it is why the PyPI package describes itself in terms of semigroup operations: any associative combine works, and nothing else does.

When I do not need a segment tree: static array with no updates is a prefix-sum array (`O(n)` build, `O(1)` query, and it beats the tree's `O(log n)` by a wide margin). Only the global minimum or maximum with pushes and pops at the end is a heap. Reads of "the range that starts here" over a sorted set of indices is `bisect`. And if all I need is range sums with point updates, a Fenwick tree does the same job in less memory and with a shorter inner loop — which is exactly the comparison on [Fenwick Tree and Segment Tree](/fenwick-tree-and-segment-tree).
