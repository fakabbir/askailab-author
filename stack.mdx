The stack is the data structure I reach for most often and understand least deeply, which is a bad combination. This page is my attempt to fix that: what the contract actually promises, what the two implementations cost, and the three problem families where a stack turns a hard problem into a linear scan.

## The contract

A stack exposes `push`, `pop`, and `peek` (plus `size`, `is_empty`) and nothing else. The ordering rule is last-in-first-out: the element I remove is the one I added most recently. That is the entire guarantee.

What the contract deliberately does *not* promise is worth stating, because it is what makes the stack efficient: no random access to the i-th element, no iteration order that I can depend on, no min or max, no removal from the middle. Every one of those extras costs something. Once I want them, I am describing a different structure — a deque if I need both ends, a priority queue if I need the extreme, a "min stack" if I need the running minimum alongside `pop`.

The invariant I rely on: **the stack holds exactly the work I have started and not finished.** That framing is what generalizes to the call stack, monotonic stacks, and iterative DFS.

## Array-backed

```python
class ArrayStack:
    def __init__(self, capacity=0, growth=2):
        self.buf = []
        self.growth = growth

    def push(self, x):
        self.buf.append(x)

    def pop(self):
        if not self.buf:
            raise IndexError("pop from empty stack")
        return self.buf.pop()

    def peek(self):
        if not self.buf:
            raise IndexError("peek at empty stack")
        return self.buf[-1]

    def __len__(self):
        return len(self.buf)
```

One contiguous buffer with a write cursor at the top. `pop` is a genuine `O(1)`: decrement the length, and since the array never shrinks on pop, no work happens at all. `push` is the interesting one, because it sometimes has to allocate a bigger buffer and copy everything.

The arithmetic: if I double on growth, the copy costs over `n` appends are `1 + 2 + 4 + ... < 2n`. So the *total* is linear, and per-append amortized cost is `O(1)`. A single `push` can still cost `O(n)`, which is why "amortized" is not a synonym for "worst case" — a latency-sensitive loop can hit the copy. The full derivation, with measured growth factors for CPython lists, is on [the amortized analysis page](/quick-hard-concept-video-this).

I measured CPython's behaviour directly:

```python
import sys

sizes = []
probe = []
for i in range(1, 65):
    probe.append(i)
    sizes.append(sys.getsizeof(probe))
print("first capacity bumps (Python list):", [n for n in range(1, 65) if sizes[n - 1] != sizes[n - 2]])
print("size in bytes at n=1,16,64:", sizes[0], sizes[15], sizes[63])
```

```text
first capacity bumps (Python list): [1, 5, 9, 17, 25, 33, 41, 53]
size in bytes at n=1,16,64: 88 184 568
```

Growth is not a clean doubling. Python over-allocates by roughly `newsize / 8 + 6` slots, which is why the bumps land at 5, 9, 17, 25, 33, 41, 53 rather than powers of two. Same asymptotic story, one more pointer-chase-free block of memory. The cost is that a Python stack of 64 elements already holds 568 bytes (8 bytes per slot plus header and slack), so "empty-ish" lists are not free.

## Node-backed

```python
class Node:
    __slots__ = ("value", "below")

    def __init__(self, value, below=None):
        self.value = value
        self.below = below


class LinkedStack:
    def __init__(self):
        self.top = None
        self.size = 0

    def push(self, x):
        self.top = Node(x, self.top)
        self.size += 1

    def pop(self):
        if self.top is None:
            raise IndexError("pop from empty stack")
        x = self.top.value
        self.top = self.top.below
        self.size -= 1
        return x

    def __len__(self):
        return self.size
```

Every `push` allocates a node, so worst case per operation is a true `O(1)` with no copy spikes ever. `pop` returns a node to the allocator, so memory tracks the live size exactly rather than the high-water mark.

| | Array-backed | Node-backed |
| --- | --- | --- |
| `push` worst case | `O(n)` on resize | `O(1)` |
| `push` amortized | `O(1)` | `O(1)` |
| `pop` | `O(1)` | `O(1)` |
| Memory | 8 bytes/slot plus slack, high-water mark | one object per live element |
| Locality | excellent, contiguous | pointer chasing, allocator-bound |
| Freed on `pop` | no | yes |

The array version wins on cache behaviour for almost every workload, and it is why every real implementation (C++ `std::stack` over a `deque` or `vector`, V8 arrays, Go slices) is array-backed. I reach for the node version in exactly two situations: I need to hand out elements to multiple owners without copying and cannot tolerate a resize spike, or the "stack" is a persistent/immutable structure where each `push` shares the tail with the previous version. In Python specifically, `list` is already array-backed, so writing my own `LinkedStack` is a teaching exercise, not a performance choice.

## The stack as the call stack

Recursion *is* a stack — the machine's, with frames holding locals, the return address, and the position in the loop. Once I see that, "rewrite recursion with an explicit stack" stops being a trick and becomes the same bookkeeping moved into code I control. The payoff is that I choose the frame contents, and I get to exceed the recursion limit.

```python
def tree_sum_dfs_recursive(node):
    if node is None:
        return 0
    return node["value"] + tree_sum_dfs_recursive(node["left"]) + tree_sum_dfs_recursive(node["leaf"])


def tree_sum_dfs_explicit(root):
    total = 0
    stack = [root] if root else []
    while stack:
        node = stack.pop()
        if node is None:
            continue
        total += node["value"]
        stack.append(node["left"])
        stack.append(node["leaf"])
    return total
```

Built as a 5000-deep left chain and run with `sys.setrecursionlimit(1000)`:

```text
recursion == explicit stack: 6
recursive version: RecursionError at depth 5000 with limit 1000
explicit stack version: 12497500 (no recursion limit)
```

The two gotchas that cost me real debugging time. First, when the order of results matters, an explicit stack reverses children relative to the recursive version — I must push them in reverse to reproduce recursive preorder. Second, a naive "push children, pop node" stack does not give me postorder, because I have no frame storing "which child did I already finish". For postorder I push `(node, visited_flag)` pairs, or I compute a preorder and reverse it. That flag in the frame is exactly the return address the machine would have stored for me.

## Monotonic stacks

The family that makes the stack worth learning beyond push/pop. The idea: keep the stack sorted in a chosen order, so any element that would break the order is popped and answered at the moment we learn its answer. Each element is pushed once and popped once, so the whole scan is `O(n)` even though the inner `while` loop looks quadratic.

```python
def next_greater(heights):
    """Monotonic stack: first element to the right that is strictly greater."""
    out = [-1] * len(heights)
    stack = []
    for i, h in enumerate(heights):
        while stack and heights[stack[-1]] < h:
            out[stack.pop()] = h
        stack.append(i)
    return out
```

```text
next greater: [3, 3, 5, -1, -1]
```

Swap the comparison direction and the stack becomes increasing instead of decreasing, which is the same code solving "previous smaller element", "daily temperatures", and "how long until something better arrives". The version that keeps *indices* instead of values is the one I use, because then the pop tells me the span width as well as the height:

```python
def largest_rectangle(histogram):
    best = 0
    stack = []
    for i, h in enumerate(histogram + [0]):
        while stack and histogram[stack[-1]] >= h:
            height = histogram[stack.pop()]
            left = stack[-1] if stack else -1
            best = max(best, height * (i - left - 1))
        stack.append(i)
    return best
```

```text
largest rectangle in [2,1,5,6,2,3]: 10
```

The `+ [0]` sentinel is the trick that makes this clean: it forces every remaining bar to be popped and measured, so I do not need a second loop. Problems in this family — largest rectangle, trapping rain water, stock-span, the next-smaller variant, minimal steps to remove an array — all reduce to "which element is the first one that breaks monotonicity, and how long was the previous one dominant?"

## Expression evaluation and bracket matching

Bracket matching is the "is the stack empty at the end" test:

```python
def balanced(code):
    pairs = {")": "(", "]": "[", "}": "{"}
    stack = []
    opening = set(pairs.values())
    for ch in code:
        if ch in opening:
            stack.append(ch)
        elif ch in pairs:
            if not stack or stack.pop() != pairs[ch]:
                return False
    return not stack
```

```text
balanced: True False
```

The two failure modes I always test are the non-empty stack at the end (`(unclosed`) and the mismatched pop (`(]`), which is why the pop check compares the *identity* of the opener rather than just emptiness.

Postfix evaluation is the other direction — numbers go on the stack, operators pop their operands:

```python
def eval_rpn(tokens):
    stack = []
    for t in tokens:
        if t in "+-*/":
            b, a = stack.pop(), stack.pop()
            stack.append({"+" : a + b, "-": a - b, "*": a * b, "/": int(a / b)}[t])
        else:
            stack.append(int(t))
    return stack[-1]
```

```text
rpn 3 4 + 2 * = 14
```

Note the operand order: `b` pops first and is the *right* operand. Getting that backwards silently breaks `-` and `/` while leaving `+` and `*` passing every test, which is the worst kind of bug. Infix is the same machinery with a precedence-aware operator stack (Dijkstra's shunting-yard), and the reason compilers and interpreters use stack machines is that this evaluation model needs no registers and no instruction scheduling.

## Where stacks show up anyway

Undo history and editor redo, browser back/forward (a stack with a cursor, not a pure stack), the call stack in every runtime and the `RecursionError` / "stack overflow" crash that ends it, DFS on graphs and trees, compilers (parse stacks, scope tables, the shadowing chain), thread-local working sets in backtracking, and the version stack in a config system. On the infrastructure side, a stack is what makes "the most recent thing wins" cheap — which is why [vector clocks and CRDT merge logic](/vector-clocks-for-crdt) need something *other* than a stack the moment two writers are concurrent. The stack answers "what do I do next", and when the answer can come from two places at once it is the wrong structure.

## Assertions, as the runnable check

```python
s = ArrayStack()
for i in range(5):
    s.push(i)
assert s.peek() == 4 and len(s) == 5
assert s.pop() == 4 and s.pop() == 3 and len(s) == 3
ls = LinkedStack()
for i in range(5):
    ls.push(i)
assert [ls.pop() for _ in range(5)] == [4, 3, 2, 1, 0]
```

All of the code above ran together with these assertions and the checks in the earlier sections, with no failures. The cases I add for anything new: `pop` and `peek` on empty raise rather than return `None` (so a bug cannot masquerade as a legitimate missing value), a `push` of `None` is allowed and must be distinguishable from empty, and the depth at which the explicit-stack version beats the recursive one is measured rather than assumed.
